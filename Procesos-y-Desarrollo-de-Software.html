Procesos y desarrollo de software

Modelos

Tradicionales

Los modelos de desarrollo organizan las actividades necesarias para construir un sistema: requerimientos, diseño, implementación, pruebas y mantenimiento. Según Sommerville, un modelo de proceso es una representación simplificada de un proceso de software y puede adaptarse a distintos proyectos.

01 Modelo en Cascada 02 Modelo en V 03 Modelo Iterativo e Incremental
01 · MODELO

Modelo en Cascada

¿Qué es?

El modelo en cascada organiza el desarrollo mediante fases separadas y ordenadas. Las actividades de especificación, desarrollo, validación y evolución se representan como etapas diferenciadas.

Es un proceso dirigido por un plan, en el que las actividades se planifican antes de comenzar el trabajo.

Diagrama del modelo

Etapas

01

Análisis

Se establecen los servicios, restricciones y objetivos mediante la consulta con los usuarios.

En esta etapa se recopilan y analizan las necesidades del usuario para definir claramente qué debe hacer el sistema.

02

Diseño

Los requerimientos se utilizan para definir la arquitectura y las principales características.

Se define cómo estará organizado el sistema, incluyendo su estructura, componentes y la forma en que funcionarán entre sí.

03

Codificación

El diseño se transforma en unidades de software y se verifica cada una de ellas.

Los programadores desarrollan el software siguiendo el diseño establecido y realizan pruebas sobre las unidades creadas.

04

Validación y Verificación

Las unidades se integran y se prueba el sistema completo.

Se comprueba que el sistema funcione correctamente y que cumpla con los requisitos establecidos al comienzo del proyecto.

05

Implementación

El sistema entra en funcionamiento.

El software se instala y se pone a disposición de los usuarios para comenzar a utilizarlo en el entorno correspondiente.

06

Evolución y Mantenimiento

Se corrigen errores, se mejora y se incorporan nuevos servicios.

Se realizan modificaciones para solucionar problemas, adaptar el sistema a nuevos cambios y agregar mejoras o funcionalidades.

✓ Ventajas

  • Las etapas están claramente definidas.
  • Facilita la planificación y el seguimiento del proyecto.
  • Está bien documentado y facilita la supervisión.
  • Puede ser adecuado cuando los requisitos son estables.

✕ Desventajas

  • Es difícil responder a cambios en los requisitos.
  • Los problemas detectados tarde pueden requerir volver etapas anteriores.
  • La separación rígida entre fases puede dificultar la adaptación.

¿Cuándo utilizarlo?

Cuando los requerimientos están bien definidos y se espera que cambien poco.

02 · MODELO

Modelo en V

¿Qué es?

El modelo en V es una variante del enfoque secuencial en la que las actividades de desarrollo se relacionan directamente con actividades de verificación y validación.

En el lado izquierdo se ubica el análisis y el diseño, y en el lado derecho las distintas etapas de pruebas. Esto ayuda a comprobar que cada fase cumple con sus objetivos.

Diagrama del modelo

Cada etapa valida un nivel concreto del producto.

Lado de desarrollo

  • Análisis de requerimientos

    Se identifican las necesidades del usuario y se establecen las funciones que deberá cumplir el sistema.

  • Diseño del sistema

    Se define cómo estará organizado el sistema y cómo se relacionarán sus diferentes partes.

  • Diseño de arquitectura

    Se establece la estructura general del software y los principales componentes que lo forman.

  • Diseño de módulos

    Se divide el sistema en módulos más pequeños, definiendo la función que tendrá cada uno.

  • Implementación

    Se desarrolla el código del sistema siguiendo el diseño y la arquitectura establecidos.

Lado de pruebas

  • Pruebas unitarias

    Se comprueba que cada componente o unidad del software funcione correctamente de manera individual.

  • Pruebas de integración

    Se verifica que los diferentes módulos funcionen correctamente cuando se conectan entre sí.

  • Pruebas del sistema

    Se prueba el sistema completo para comprobar que cumple con los requisitos establecidos.

  • Pruebas de aceptación

    Se verifica que el sistema responda a las necesidades del usuario y esté listo para su entrega.

✓ Ventajas

  • Relaciona las etapas de desarrollo con las pruebas correspondientes.
  • Permite planificar las pruebas desde etapas tempranas.
  • Facilita la organización estructurada del proyecto.
  • Hace explícita la relación entre verificación y validación.

✕ Desventajas

  • Es poco flexible ante cambios importantes de requisitos.
  • Un producto funcional suele aparecer recién hacia las últimas etapas.
  • Durante las pruebas, los cambios importantes de diseño son difíciles.

¿Cuándo utilizarlo?

En proyectos con requerimientos claros que necesitan un proceso estructurado de verificación y validación.

03 · MODELO

Modelo Iterativo e Incremental

¿Qué es?

La especificación, el desarrollo y la validación están vinculados. El sistema se construye mediante versiones llamadas incrementos, y cada una agrega nuevas funcionalidades.

El desarrollo se repite en ciclos, permitiendo revisar y mejorar el sistema a medida que avanza. Los primeros incrementos pueden incluir funciones prioritarias y luego ir creciendo.

Diagrama del modelo

¿Cómo funciona?

Cada incremento entrega una versión con una funcionalidad nueva y el producto va evolucionando.

✓ Ventajas

  • Permite incorporar cambios con mayor facilidad.
  • El cliente puede probar versiones tempranas del producto.
  • Se adapta mejor a requisitos cambiantes o no completamente definidos.
  • Reduce el riesgo de entregar un sistema muy tarde o con fallos graves.

✕ Desventajas

  • El proceso puede ser menos visible para los administradores.
  • La estructura puede ser difícil de gestionar si no se realiza una refactorización adecuada.
  • Los sistemas grandes pueden requerir una coordinación más compleja.
  • Los requisitos y responsabilidades deben estar claras desde el inicio.

¿Cuándo utilizarlo?

Cuando los requerimientos pueden cambiar y se necesitan versiones funcionales de forma progresiva.

i

Los modelos no son mutuamente excluyentes. En proyectos grandes pueden combinarse: algunas partes pueden desarrollarse mediante cascada y otras mediante un enfoque incremental, según las características de cada parte del sistema.
